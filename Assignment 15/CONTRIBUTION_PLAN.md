## Strategy Overview

My approach is to start with documentation and test contributions
(low risk, easy to get merged) and then move to small feature additions.
Every contribution follows the host repo's CONTRIBUTING.md exactly -
matching their coding style, running their tests before pushing, and
keeping PRs small and focused.

Before writing a single line of code, I comment on the issue to avoid
duplication: *"Hi, I'd like to work on this - planning to submit a PR
by [date]."* This is standard open-source etiquette and increases
acceptance rate significantly.

## Contribution Priority

1. **Documentation first** - README fixes, typo corrections, missing setup steps.
   These are always welcomed, rarely rejected, and build rapport with the maintainer.

2. **Tests second** - Adding missing test cases.
   Every project benefits from higher coverage and maintainers appreciate it.

3. **Features third** - Small, self-contained features from `good-first-issue` labels.
   Discuss the approach in the issue comments first, then implement.

---

## PR Quality Checklist (self-review before every submission)

- [ ] Read the project's CONTRIBUTING.md before touching any code
- [ ] Commented on the issue to claim it
- [ ] Created a branch with a descriptive name (`fix/readme-typo`, `test/add-service-tests`)
- [ ] Made one focused change (not multiple unrelated things in one PR)
- [ ] All existing tests pass locally
- [ ] New tests written where applicable
- [ ] PR title is clear and descriptive
- [ ] PR body links to the issue (`Closes #X`)
- [ ] PR body explains what changed and why
